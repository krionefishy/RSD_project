# Правила новых микросервисов

## 1. Базовый принцип

Новый микросервис повторяет архитектуру основного backend-сервиса:

```text
<service>/
├── app/
│   ├── main.py
│   ├── application.py
│   ├── api/router.py
│   └── <domain>/
│       ├── api/
│       ├── usecases/
│       ├── domain.py
│       ├── dto.py
│       └── db_models.py
├── migrations/
├── storage/
│   ├── pg/
│   ├── redis/
│   └── s3/
├── tests/
├── Dockerfile
└── docker-entrypoint.sh
```

API, use case, domain, DTO, DB models и DI оформляются по тем же правилам, что и в основном приложении.

## 2. Владение данными

У каждого микросервиса есть только своя БД:

- отдельный database/schema/user;
- свои SQLAlchemy модели;
- свои Alembic миграции;
- сервис сам владеет своими таблицами и не пишет напрямую в таблицы другого сервиса.

Если сервису нужны данные основного приложения для чтения, предпочтительный вариант — читать из read-replica основной БД или из отдельной read model. Запись в основную БД напрямую запрещена.

## 3. Shared-инфраструктура

Микросервисы не поднимают собственные Kafka, S3 и Redis.

Используются общие shared-инстансы:

- Kafka — общий broker/cluster, свои topics и consumer groups;
- S3 — общий endpoint/bucket/prefix policy по необходимости;
- Redis — общий Redis, отдельные key prefixes/db только если нужно.

В docker compose микросервис получает host/credentials общих сервисов через env/config, но не добавляет свои отдельные контейнеры Kafka/S3/Redis.

## 4. DI и зависимости

У каждого микросервиса должен быть свой локальный набор DI providers. Нельзя импортировать `ALL_PROVIDERS` основного backend, если они тянут домены монолита (`auth`, `users`, `knowledge_base` и т.д.).

Разрешено переиспользовать общие инфраструктурные клиенты и config loader, если они не создают зависимости на домены другого приложения.

## 5. Отчеты и тяжелые вычисления

Report-service:

- читает данные для отчетов из read-replica основной БД или read model;
- хранит у себя только метаданные отчетов, статусы, ошибки, S3 keys и параметры запуска;
- загружает готовые файлы в shared S3;
- не выполняет тяжелый CPU/blocking parsing/generation прямо в event loop.

Парсинг и составление отчетов запускаются через выделение работы в thread:

```python
result = await asyncio.to_thread(blocking_parser, payload)
```

Если вычисления станут длительными и массовыми, сценарий выносится в очередь + worker, но HTTP API все равно не должен блокировать event loop.

## 6. Кассовый ingestion-service

Cash-ingestion-service:

- принимает события продаж от кассовых систем;
- валидирует вход и идемпотентность;
- сохраняет входящее событие в свою БД;
- публикует событие в shared Kafka;
- не отправляет продажи в основной сервис прямым HTTP потоком.

Его БД может использоваться для технического аудита, повторной доставки, dead-letter записей и отдельной аналитики по входящему потоку.
