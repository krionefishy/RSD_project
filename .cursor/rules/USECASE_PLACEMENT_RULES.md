# Правило расположения use case по минимальной роли

## 1. Базовый принцип

Use case располагается в блоке роли с наименьшим уровнем прав среди всех ролей, которым доступен этот сценарий.

Если сценарий доступен обычному пользователю, его нельзя размещать в `admin`, даже если администраторы тоже имеют к нему доступ. Администратор должен переиспользовать этот use case и получать расширенную область видимости через параметры контекста и проверки доступа.

## 2. Иерархия ролей

От меньших прав к большим:

1. `seller` / `user`
2. `manager`
3. `admin_staff` / `admin_education` / `admin_sales`
4. `root_admin`
5. `super_admin`

В продуктовых требованиях роль `user` соответствует обычному сотруднику/продавцу; в коде значение роли хранится как `seller`.

## 3. Как выбирать место

| Доступ к сценарию | Где располагать use case |
| --- | --- |
| Доступен пользователю и старшим ролям | В пользовательском блоке, например `backend/app/users/usecases/...` или в доменном модуле с пользовательским доступом, но не в `admin` |
| Доступен менеджеру и старшим ролям, но не пользователю | В блоке/модуле менеджерского сценария; при отсутствии отдельного backend-модуля менеджера допускается доменный модуль, но не `admin`, если сценарий не является административным |
| Доступен только `admin_staff` и старшим ролям | В `backend/app/admin/staff_admin/usecases/...` или в доменном модуле персонала, если сценарий не завязан на административный namespace API |
| Доступен только `admin_education` и старшим ролям | В `backend/app/admin/educ_admin/usecases/...` или в доменном модуле обучения |
| Доступен только `admin_sales` и старшим ролям | В `backend/app/admin/sales_admin/usecases/...` или в доменном модуле продаж |
| Доступен только `root_admin` и `super_admin` | В `backend/app/admin/software_admin/usecases/...` |
| Доступен только `super_admin` | В `backend/app/admin/super_admin/usecases/...` |

## 4. Правило для повторного использования

Если старшая роль выполняет тот же сценарий, что и младшая, новый use case не создается. Нужно переиспользовать use case младшей роли и расширить только scope проверки:

- пользователь видит только свои данные;
- менеджер видит данные сотрудников своего блока;
- `admin_staff` видит все данные персонала;
- `root_admin` и `super_admin` видят все данные без ограничений по блокам и точкам.

Пример: просмотр профиля доступен пользователю, менеджеру, `admin_staff`, `root_admin`, `super_admin`. Значит use case находится в пользовательском блоке, а старшие роли проходят через тот же сценарий с проверкой области видимости.

## 5. Запрет на дублирование

Запрещено создавать отдельные административные копии use case вида `AdminGetUserProfileUseCase`, если уже существует пользовательский `GetUserProfileUseCase`, который можно безопасно расширить проверкой роли и области видимости.

Допустимое исключение: сценарий старшей роли имеет другой бизнес-смысл, меняет данные или требует отдельной транзакционной логики. Например, "просмотр своей ставки" и "заполнение ставки сотрудника" являются разными use cases.
